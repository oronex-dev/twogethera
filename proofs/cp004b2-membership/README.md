# CP-004B.2 — local authenticated membership command proof

Disposable, headless security experiment. **Not a production migration or Flutter integration.** See [the implementation report](../../docs/CP-004B2.md) for exact results and limitations. Existing CP-004A/B.1 proofs and application configuration are preserved.

## Run

From the repository root, with local OrbStack running, Python 3, and Supabase CLI **2.122.0**:

```sh
rtk proxy python3 -u proofs/cp004b2-membership/start_local.py
rtk proxy python3 -u proofs/cp004b2-membership/run_tests.py
```

Expected result: **38 real Auth/HTTP/database scenarios passed; zero mocks/skips**. Missing services, nonlocal endpoints, unsafe role/marker collisions and unobserved race barriers fail the run. Do not use optimized Python. Normal client requests use only the public local API key plus genuine user access tokens. Administrative Auth calls create synthetic confirmed fixtures only; database operator calls install/reset/inspect the proof and coordinate fault/race barriers. No client authorization assertion is made using a service-role bearer token.

The startup helper captures credential-bearing CLI output rather than printing it. Do not replace it with raw status/start output or enable HTTP/SQL debugging. It starts `twogethera-b2` on a loopback-only Docker bridge with API `127.0.0.1:56321`, database port `56322`, shadow port `56320` and local mail capture `56324`. It does not use/reset the root development stack or `twogethera-b1`. Storage, Realtime, Studio, analytics and other unused services are excluded. Signing material is generated by the CLI into ignored `supabase/.local/signing_keys.json`, with directory mode 0700 and file mode 0600. It is never a versioned artifact.

The runner validates engine/context, project labels and actual published addresses before mutation. Each application-schema reset verifies the disposable database marker. It manually installs `supabase/migrations/20261029000200_commands.sql` inside this folder; automatic migration/seed execution is disabled. Never copy the prototype into root `supabase/migrations/` or run it against a hosted project.

## Scope and reset boundaries

Six small tables: spaces, memberships, private account availability, invitation digests, keyed recipient binding and operation receipts. There are no product records, client sessions, archive reads, account deletion or retention jobs. Repeated runs replace **only these two proof-owned schemas** in the guarded B.2 database. Each scenario group gets fresh application state; durable replay tests retain the same state across independent HTTP requests. Synthetic Auth users accumulate with unique run identifiers and reserved `example.invalid` addresses; no existing Auth users are deleted. Remove the dedicated disposable stack/volumes only through a separately reviewed local cleanup command; this runner does not prune Docker or delete other stacks.

The runner narrows PostgREST to `cp004b2` and this stack's public ES256 JWKS, excluding legacy shared-development HS256 user-token verification. It restarts only B.2 PostgREST after installing database logging defaults. Root/B.1 Auth configuration is unchanged. The SQL bootstrap temporarily grants schema CREATE to `supabase_auth_admin` solely to transfer the current-user email helper's ownership, then revokes it; the function cannot accept an arbitrary user ID or be executed by API roles. This privileged local bootstrap is a production portability/review boundary.

## Command contract

All commands are POST RPCs under `/rest/v1/rpc/`, with `Content-Profile: cp004b2`. Reads use `Accept-Profile: cp004b2`. No elevated key is required by ordinary clients. Actor identity always comes from verified JWT context, never a payload member ID.

| Command | Parameters | Result |
| --- | --- | --- |
| `ensure_account` | none | Own `user_id`; never re-enables disabled accounts |
| `account_context` | none | Own `user_id` and currently authorized space/state/epoch projections |
| `create_space` | `p_operation_id` UUID | `space_id`; one draft with immutable seat 1 |
| `issue_invitation` | operation UUID, `p_space`, `p_expected_epoch`, `p_email` | First success: invitation UUID, server expiry and raw token; retry: same UUID/expiry only |
| `accept_invitation` | operation UUID, `p_token` | `space_id`; intended currently verified recipient occupies seat 2 |
| `revoke_invitation` | operation UUID, `p_invitation` | Invitation UUID and `revoked: true` |
| `leave_space` | `p_space`, `p_expected_epoch` | `true`; irreversible experimental closure and immediate former-scope denial |
| `can_read` | `c` space UUID | Boolean for the caller's current scope only |

Operation UUID parameter name is `p_operation_id` for all four idempotent commands. Authenticated reads expose only `spaces` and `memberships`, filtered by RLS. No direct table writes or private schema access are granted. Failure statuses: unauthenticated 401/403; generic sensitive command denial 403/`unavailable`; malformed email/self-invite/null operation ID 400; operation-ID payload mismatch/second active space 409. RLS-filtered foreign SELECT is 200 with `[]`, not a 403. PostgreSQL SQLSTATE `42501`, `PT400` and `PT409` are deliberately mapped through actual PostgREST behavior.

## Non-enumerating invitation issuance

A valid unrelated email receives the same opaque issuance envelope whether registered, unverified, unregistered or already in another space. **Issuance is provisional; it does not assert the recipient is verified.** Current verified email, account availability and capacity are mandatory at acceptance. The implementation deliberately performs no recipient Auth directory lookup when issuing. This resolves the privacy tension between verified-recipient acceptance and registration enumeration without returning a registration oracle. Invalid/self emails can be rejected because that discloses no unrelated registration status.

One pending invite per draft; a fresh issue operation explicitly revokes the previous pending token. Tokens are 32 random bytes encoded as 64 lowercase hex characters, expire after 24 server hours, and are stored only as SHA-256 digests. Email binding stores HMAC-SHA-256 under a private random versioned key, not plaintext email or an enumerable plain email hash. Normalization trims surrounding whitespace and lowercases only the domain; no plus/dot/provider aliases or local-part folding are assumed. Full internationalized email/canonicalization policy needs review.

**Raw token delivery is once only.** The receipt stores metadata, never the token. After a lost issue response, replay returns the original metadata; the token cannot be recovered. A client must explicitly replace/revoke the invitation with a fresh operation to obtain a fresh token. No email delivery, clipboard/share integration or token-recovery endpoint exists. Never put these tokens in query-string logs or client analytics. Equal error envelopes are tested; constant-time behavior across all failure paths is not claimed.

## Security limits

This proof is not production readiness. Account/space locks and constraints are real, but the suite is bounded, not an exhaustive scheduler/model checker. Auth-owned row-lock ordering requires a full GoTrue/hosted permissions review before promotion. The private HMAC key is in trusted-server database storage for the experiment; production key custody, rotation and backup handling are unresolved. There are no rate limits at the command layer, delivery anti-abuse controls, receipt cleanup/quotas, production telemetry or staged upgrades.

All commands check live verified/nonanonymous/nonbanned Auth identity; RLS reads check JWT identity plus live private account availability/membership/space state. Auth ban/signout alone is **not** proven to instantly invalidate existing JWT reads; disable the private account gate or revoke membership for immediate application-scope denial. No guarantee is made about remotely erasing data already downloaded. Closed-space data is inaccessible to both former members in this experiment; archive ownership/eligibility/retention remains pending and unimplemented.

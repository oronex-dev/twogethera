# CP-006 — Partner Linking Readiness

**Review date:** 2 November 2026

**Scope:** architecture decision recording and readiness audit only. No partner-linking code, migration, Auth change, UI change, dependency, hosted connection, invitation delivery or commit is included.

## Executive recommendation

**READY TO IMPLEMENT as a bounded local-only membership and invitation milestone**, after review of this report. D06 and D09 are formally approved and do not need another product approval. CP-006 must implement only setup, invitation, verified acceptance, membership state, and immediate unlink revocation. Do not implement planner modules or archived-content retention, recovery, audit history, export, Storage or Realtime in this slice.

One important compatibility gap is recorded: CP-004A's prototype `can_read` predicate includes `draft`, and the `records` SELECT policy uses that predicate. Code inspection therefore shows an unpaired member would be permitted to read a minimal shared test record; the 28-case suite did not specifically exercise that draft-record read. That prototype predates D09 approval. Preserve its historical results, but do not port that predicate unchanged. CP-006 acceptance tests must establish that an unpaired account cannot read or write any shared planner content.

P03, P04 and P09 do not block isolated linking, invitation, pairing and access revocation when the database contains no product content and archive content endpoints remain unavailable. They do block implementing archive record reads/exports, ordinary text restore, and retained financial audit behavior. D06 abuse-limit thresholds and identity/key handling are implementation requirements to specify and test; the requirement to have limits is already approved.

This readiness report is not authorization to start implementation. The present task explicitly stops at documentation for review.

## Formal approvals and current status

### D06 — Invitation Security: formally approved

Adopted exactly as instructed: invitations bind to a verified recipient email; use a single-use 256-bit token; expire after 24 hours; acceptance is atomic; duplicate/replay requests are safely idempotent; and creation and acceptance have abuse limits. No automatic delivery or different-recipient fallback is inferred. Numeric limits, email comparison and HMAC/key-rotation details are implementation/security choices that still require testable definitions.

### D09 — Couple-Space Access: formally approved

Adopted exactly as instructed: shared planner writes require exactly two active linked members; unpaired accounts may use setup and invitation flows but cannot access shared planner content; archived spaces permit only read/export/privacy-removal operations; and third or replacement members cannot join an existing space. This does not specify which archive records are eligible or how long they remain accessible.

## Repository readiness audit

### Existing pieces to reuse as references

- CP-004B.2 demonstrates a small authenticated command surface instead of client table writes: `create_space`, `issue_invitation`, `accept_invitation`, `revoke_invitation`, `leave_space`, and a current account/space context.
- Existing SQL shows how to derive actor from `auth.uid()`, validate current verified Auth email, gate active account state, lock actor/scope/invite rows, enforce unique active membership and seats, and commit invite consumption, membership changes, epoch changes and idempotency receipt together.
- Existing runners provide local-only Supabase startup, synthetic confirmed fixtures, signed Auth tokens, PostgREST calls, isolated database sentinels, log/token scans, fault injection and real independent-connection race barriers.
- CP-005C provides local/debug Riverpod auth state, lifecycle repository/controller, route protection and synthetic-only authentication UX. The existing repository can later gain a narrow membership command capability without changing session authority or approved visual design.

### Missing CP-006 functionality

- No production/application migration, schema, RLS policy, RPC grant, trigger, view or client-facing partner-linking command exists in root `supabase/migrations/` (none is present).
- The app has no couple-space creation/invitation/acceptance/unlink repository methods, domain state, setup/invite routes or membership status UX.
- Existing prototype fixtures use local synthetic users. Production Auth configuration, verified-email-change semantics, binding-key custody/rotation, token delivery UX and operational limits are not finalized.
- The CP-004B.2 prototype has no shared planner content table, so its RLS tests cannot prove D09's unpaired-content denial. CP-004A does contain a minimal record and its `can_read` accepts `draft` or `paired`; the draft record can therefore be read. This is a known prototype mismatch against the newly approved D09 policy, not evidence of a production data exposure.
- B.4's successful-issue quota does not limit acceptance attempts or cover source/IP/distributed abuse. D06 requires controls on both creation and acceptance.
- Existing proof link/unlink outcomes are bounded local proof evidence, not production job/session/cache/Storage/Realtime revocation guarantees. Current membership/account state must gate every future request, even if the signed JWT has not expired.
- Root local Auth has email confirmations disabled. A successful local password sign-in alone must not be treated as proof of verified-email identity.

### Authorization and privacy boundary

Every new authenticated command must derive the actor from the signed JWT (`auth.uid()`), then check current account and membership rows inside the transaction. Do not rely on a valid signature, stale client context, user metadata, a cached couple ID or an invitation token as current authorization. After a committed unlink, every subsequent RPC/read under the same still-valid JWT must be denied for the former shared scope. An already-running request or bytes already delivered cannot be recalled; tests must establish the post-commit boundary and say so.

For D09, unpaired setup metadata/invitation status must use an explicit narrow projection. It must not share a broad `can_read_space` predicate with records, aggregates, search, media, sync pages or exports. Active paired shared planner writes must recheck exactly two active members after locking; constraints and unique active membership are backstops, not a reason to trust a prior count. Archived invitation/create/write paths are denied. Archive read/export must remain unavailable for content until P03/P04/P09 provide record eligibility and retention; no replacement member can acquire the closed scope. Privacy removal, once relevant content exists, must be a separate narrowly authorized lifecycle command, not general archive write permission.

## Proposed CP-006 implementation sequence

Each checkpoint stays on local synthetic infrastructure, separated from root production migrations until reviewed. No hosted project, live email delivery, shared feature table, Storage or Realtime policy is needed.

1. **CP-006A — Translate approved policy to a minimal contract.** Freeze names/state transitions, operation IDs, verified-email comparison behavior, token response rules, and configurable issue/accept abuse limits. Define an unpaired setup projection separate from planner reads. Record which archive actions are unavailable until P03/P04/P09. Add a new isolated proof project; do not edit CP-004 proofs.
2. **CP-006B — Schema, grants and RLS proof.** Add only Auth identity/account gate, couple space, two historical member seats, private invite, safe operation receipt, and minimal D09 test record. Use restrictive API schemas/grants and authenticated RPC only. Enforce one active space/account, maximum two active members, no seat/space reuse after archive, and no planner record visible to an unpaired account.
3. **CP-006C — Create and issue.** Prove authenticated space creation and recipient-bound invitation issue/revoke. Generate 32 random bytes from a CSPRNG; persist only a token digest and protected recipient binding, return the token once, set a server-time 24-hour deadline, and omit it from receipt/log/error/URL/storage. Apply issue abuse budget; exact thresholds remain explicitly recorded implementation values, not silently approved UX promises.
4. **CP-006D — Atomic acceptance and replay.** Verify real local Auth JWT and current verified email after acquiring canonical locks. Commit acceptance, second active membership, paired state, authorization epoch, idempotency receipt and invite consumption in one transaction. Prove exact retry returns a safe result, conflicting operation reuse fails, token replay is generic, concurrent same-invite acceptance creates one member, and one user cannot win two simultaneous invitations.
5. **CP-006E — Revoke, expire and unlink.** Add revoke/expiry and either-member unlink. Recheck live membership/account state after locks. Revoke the leaver and pending invitations, close the scope irreversibly, and deny all later former-scope server access with the same unexpired JWT. Do not expose archive content, export, ordinary recovery or financial audit data.
6. **CP-006F — Flutter setup and invitation UX.** Only after backend HTTP/RLS/concurrency gates pass, add a small Riverpod/go_router setup/invitation flow using the existing auth repository/controller boundaries and approved CP-003A/CP-005C visuals. Keep the preview honest about manual sharing, verified recipient, 24-hour expiry, one-use behavior, pairing requirement and the fact that shared content is unavailable before pairing. Keep sessions RAM-only and do not add offline acceptance.

## Required automated tests

### PostgreSQL constraints and RLS

- Fresh database bootstrap and safe N-1 upgrade within the dedicated proof project; root Supabase schema/config remains untouched.
- Exactly one active couple per account; active member cap of two; seat/user uniqueness; commit-time state/cardinality validation; immutable closed/archive state and rejection of replacement/historical seat reuse.
- Anonymous and unrelated users cannot read private invites or another scope. Setup account sees only its own setup/invite projections.
- Unpaired account gets no shared planner record rows or aggregates through direct REST table access, RPC, view, search, sync, count or guessed identifiers. Include the CP-004A regression case.
- Exactly-two paired members can perform only the authorized shared test operation; third-member attempts, direct DML, scope/actor substitution, archive mutations and malformed RPCs fail.
- Archived space allows no invite, acceptance, planner mutation, ledger write, or ordinary restore. Any archive read/export fixture must be withheld pending P03/P04/P09; privacy-removal behavior is tested only as a narrow non-content state transition.

### D06 identity, abuse, idempotency and races

- Invitation accepted only by the intended current verified Auth email; reject anonymous, unverified, wrong email, changed email, banned/disabled account, self-accept and an account already in another active couple. Use only `example.invalid` synthetic accounts.
- Check 256-bit CSPRNG token generation/shape and uniqueness; raw token is returned once and absent from database projections except digest, receipts, HTTP errors, logs, test reports and durable Flutter storage.
- Server-clock expiry at boundary and after 24 hours; revoked/consumed invitations and a third/replacement user fail generically without partial effects.
- Idempotent exact retries do not duplicate space/membership/receipt effects. Reused operation ID with changed payload is rejected. A retry after response loss cannot recover the plaintext token.
- Concurrent same-token accept, concurrent accepts into separate spaces by the same user, create/accept capacity race, invite replacement/revoke versus accept, unlink versus accept, expiry versus accept, and late-error transaction rollback, using independent DB connections and observed lock barriers.
- Separate creation and acceptance abuse budgets, including atomic exhaustion under concurrency, safe reset/window behavior, generic responses, bounded request size and no paid external limiter assumption. Numeric thresholds must be written in the CP-006 implementation plan/config and tested; B.4's existing issue-only quota is not sufficient.

### Revocation and client integration

- After unlink commits, reuse the exact same valid JWT for PostgREST table reads, RPCs and context refresh; assert no old-couple data and no successful writes. Distinguish expected RLS-empty reads from explicit denials. Verify a racing operation either commits before closure or fails after it, never after the revocation barrier.
- Confirm account suspension and membership revocation are authoritative database checks, not only Auth sign-out/refresh-session revocation.
- Flutter Riverpod state responds to create/invite/accept/revoke/unlink results, rejects stale context, never trusts cached membership on reconnect, does not retain invitation tokens, and does not change CP-005C session persistence or visual design.
- Real Chrome/Android/iOS local API requests after pairing; repeat critical old-token/cross-couple negatives. Unit/widget tests supplement, not replace, real Auth → JWT → PostgREST → `auth.uid()` → RLS tests.

## Unresolved policy gates and scope

- **P03:** blocks who may read/export retained shared archive records, ownership/classification, closure expiry and mixed-content treatment. CP-006 may close a scope and deny content; it must not create an indefinite archive.
- **P04:** blocks ordinary shared-text restore/trash; do not create a text recovery mechanism.
- **P09:** blocks retained financial audit purpose/audience/retention; no ledger table/history or 365-day default in this milestone.
- D03 remains a recorded revision, not a complete implementation policy. P01/P02/P05/P06/P07/P08/D04/D05/D07/D08/D10/D11 remain pending formal approval and bound later modules.
- Numeric invite abuse-limit thresholds are not specified by D06 approval; the existence of both create and accept controls is approved. Choose/test operational thresholds as part of the implementation plan and distinguish local proof settings from production promises.
- Root local Auth confirmation is disabled, and local proof stacks are not independent production auth environments. Use the isolated project's trusted synthetic verified/unverified fixtures; do not alter root Auth config without separate authorization.

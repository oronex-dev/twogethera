## State and credential handling

The existing Riverpod controller, repository generations, explicitly accepted session ownership, single-flight refresh, logout revocation and protected `go_router` checks remain authoritative. Form handlers also reject duplicate pending submissions. Password/confirmation/link text is cleared before awaiting the backend and controllers are disposed on route disposal. Clearing a Dart string reference is not guaranteed RAM zeroization. Password manager autofill, autocorrection, suggestions and personalized IME learning are disabled for credential fields. This reduces app-requested persistence; it cannot control an external keyboard, password manager or operating system.

Display name is stored through supported Supabase Auth signup metadata. It is untrusted display-only input, bounded when projected into the authorized account context and never used for authorization. No profile table or schema migration was added. Resend uses the existing SDK's signup resend operation, with identical public feedback for account-specific failures; it does not prove delivery. Network failures remain distinguishable from generic account eligibility, and server rate limits remain authoritative.

Returning from a loading/recovering email flow signs out/cancels accepted local authority before navigation, avoiding late recovery completion after cancellation. Account projections are rendered only in `authenticated`; loading, suspension, expiry and sign-out remove them. Interrupted password-update feedback explicitly allows an ambiguous server outcome: use fresh sign-in or a new recovery request rather than assuming the password was unchanged.

### Local callback boundary

The debug route accepts exactly one `token_hash` and one `type=signup|recovery`, without fragments or additional parameters. Both plain hexadecimal hashes and the genuine local Auth `pkce_`-prefixed hash format are supported; this is token-hash verification, not authorization-code exchange. It reconstructs a fixed allowlisted local Auth verification URL; it never follows an arbitrary pasted destination. Browser `history.replaceState` removes the current entry's query and fragment before verification starts. Unsupported PKCE codes, implicit access/refresh tokens, duplicate parameters and malformed hashes fail safely. The repository still validates local origin, port, path and flow type.

Manual Mailpit link paste is supported on all platforms. A native router callback is not evidence of automatic OS email delivery: universal/app links, associated domains, custom-scheme registration and production email redirects are not configured in this milestone. The stock local email URL points to Auth, not directly to this new app route. A production PKCE/callback design and cold-start behavior need a separate security-reviewed milestone. Address replacement cannot erase mail history, external logs, previously copied links or every browser history entry. Tokens must never be logged or included in screenshots/reports.

The driver now settles viewport changes and starts genuine network actions in `runAsync`; assertions and the original security suites were not weakened. The callback allowlist was corrected for that exact format and covered by real confirmation/recovery and ordering tests. Earlier failing development attempts are not counted as passing results.

Native field-value assertions and genuine HTTP traces then reproduced the input problem: the intended retry text did not replace the existing field value, and no second sign-in or known-address recovery HTTP request was sent. The native runner initializes its binding before `main`, so creating a replacement binding was rejected before any tests ran; this harness setup was corrected to use the existing binding. Field-value and server-response assertions remain in place. This is real native rendering/Auth/API validation with automated keyboard injection, **not** OS-keyboard/IME acceptance evidence. Actual device keyboard/autofill interaction still needs manual testing. The intermediate instrumented run passed 1/4 and failed on these field assertions; it is not included in successful totals.

## Remaining production work and limitations

- This is a local/debug UX milestone, not production authentication readiness.
- Production email delivery, abuse controls, verified redirect/callback allowlists, native mail-app routing and cross-device recovery require their own reviewed scope. The local hash-link flow trusts possession of the local mailbox link; it does not add initiator/expected-account binding or production login-CSRF protection. A production flow must review PKCE/state/account binding and explicit identity confirmation before enabling external callback delivery.
- RAM-only sessions intentionally end on app process termination, browser reload or tab replacement. No persistent login or automatic refresh was enabled.
- Issued JWTs may remain valid until expiry after logout/reset; offline logout cannot claim confirmed server revocation.
- Recovery-only mode is a client UX boundary, not a new server-side Auth privilege restriction. Existing proof limitations and unresolved product/privacy decisions remain pending.
- Storage inspection cannot prove forensic erasure or inspect all OS/keyboard/keychain/browser-internal copies. Manual screen-reader testing and real physical devices remain necessary before production.
- No OAuth, partner linking, shared data, account deletion/retention, paid service, deployment, automatic CP-005C commit or push is included.

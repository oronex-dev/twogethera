### Storage proof and supported process lifecycle

The existing suite's nonce-protected in-flight audit remains intact. A new, separate `test_local/native_restart_probe.dart` target strengthens verification beyond a new Dart repository instance. It uses the unchanged application, controller and real local Auth adapter; `lib/main.dart` never references it, and it refuses web/release operation.

After the native integration suite, the runner uses Flutter's supported `run --debug --no-resident` launcher for the first install/launch only (Android additionally uses `--no-hot`). The second launch uses `xcrun simctl launch` or Android `am start` directly, without any rebuild or reinstall. The installed SDK's simulator launch/install and runner cleanup behavior were inspected. The proof:

1. Signs in and verifies real authorized account context/protected routing in the first OS process.
2. Supplies the newly generated access/refresh tokens only to the nonce-protected loopback controller's RAM. They are not logged or saved as results. The controller verifies that the original JWT is accepted by the real account-context API.
3. Audits app storage while live, writes an unrelated random witness in the app's data directory, and terminates the authenticated OS process without a client clear, disposal, logout or server revocation.
4. Audits the retained data after process death, then launches the same already installed target again through the native OS command. The data witness must survive; iOS must retain the exact same data-container path. An uninstall/data clear or replacement container cannot satisfy this proof.
5. Requires the cold process to remain signed out, deny protected routing and fail account-context retrieval without a new sign-in. The old JWT must still succeed at the server, ruling out server expiry/revocation as an explanation for the cold-client denial.
6. Repeats the storage audit after relaunch and removes only its own witness. It terminates its test probe afterward.

The original scoped secret/JWT pattern scan is retained. The additional exact-token scan covers **all private application files, including caches**, searching across chunk boundaries on iOS. This avoids confusing compiled public keys/synthetic fixture constants with dynamically issued session credentials. Keychain/Keystore and OS forensic erasure remain outside the filesystem check; the adapter has no persistence plugin/backend, and the real restart check independently verifies no automatic session recovery. Synthetic fixture bundles remain ignored test artifacts and must not be published.

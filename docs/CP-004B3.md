## Migration rehearsal and implemented safeguards

Three reviewed, checksummed slices are in the [manifest](../proofs/cp004b3-rehearsal/migrations.json):

| Order | Slice | Responsibility |
| --- | --- | --- |
| 001 | [bootstrap](../proofs/cp004b3-rehearsal/supabase/migrations/20261029000100_bootstrap.sql) | Marked nonlogin owner, no elevated attributes or role memberships in either direction; pgcrypto/version/schema prerequisites; Auth REFERENCES only |
| 002 | [kernel](../proofs/cp004b3-rehearsal/supabase/migrations/20261029000200_kernel.sql) | B.2 tables, constraints, RLS, guarded commands, grants and narrow Auth-owner helper |
| 003 | [default execution](../proofs/cp004b3-rehearsal/supabase/migrations/20261029000300_default_execution.sql) | Application-owner global default EXECUTE revoked from PUBLIC and client roles |

Object names remain `cp004b2`/`cp004b2_private` in a distinct physical cluster to run the exact checkpointed B.2 methods. The kernel is the B.2 snapshot with only its heading, B.3 target marker and transaction wrapper changed. The runner owns the transaction so DDL, privilege changes and private migration-ledger insertion commit together. It imports the original B.2 runner without editing it and pins that source checksum. PostgREST exposes only the intended API schema; migration ledger and private tables/helpers are unavailable to clients. Automatic Supabase migration/seed execution is disabled. This custom rehearsal ledger is not Supabase production migration history.

Verified sequence: reject kernel-before-bootstrap; apply prerequisites; inject an error after kernel/grant creation and prove all kernel schemas/ledger effects roll back; apply kernel normally; reproduce B.2 defaults in the isolated N-1 environment; create a real-JWT paired space with invitations/receipts; apply hardening; compare six-table content digests including HMAC material; verify current/cross-scope HTTP results; rerun without reapplying; reject checksum drift; rebuild the empty application schema twice from ordered files. Auth users/database volumes are never dropped. The private migration ledger has no client access.

The harness is a **single-runner local tool**, not a production concurrent deployer. It resets only its guarded three schema namespaces; it does not handle production data repair, vendor migration-history adoption, every crash schedule or online index installation. No whole-database `db reset`, hosted migration or production rollback is performed. A fresh local Supabase stack was actually started; repeated tests prove application-schema reconstruction, not repeated empty-volume creation or restore of managed Auth schemas.

## Security audit findings and resolution status

| ID | Finding and evidence | Resolution/status |
| --- | --- | --- |
| F01 | A/B.1/B.2 use per-schema default EXECUTE revokes. A harmless future B.2-owner definer canary still receives PUBLIC EXECUTE under the global factory default. Existing installed functions are explicitly revoked, so this is a future-migration exposure gap, not a demonstrated cross-couple leak in existing commands. | **Fixed in B.3 slice 003**, globally for the application owner in this disposable DB. New canary has no client EXECUTE and gets HTTP 403; removed after test. Historical proofs remain frozen. Promote the rule to any reviewed future migrations. |
| F02 | B.2 owner-collision check verifies inbound membership only; an owner could inherit another role without changing its NOLOGIN/NOBYPASSRLS attributes. This requires a privileged grant, not an ordinary-client exploit. | **Hardened in B.3 bootstrap:** reject membership in either direction and unsafe attributes/marker. Real SQL fault probes add each direction, prove bootstrap denial, then revoke the temporary grants. |
| F03 | Current verified email relies on a narrow definer owned by `supabase_auth_admin`. Application owner has no broad Auth SELECT; client cannot execute the bridge or supply another UID. The owner nevertheless has extensive managed Auth privileges. | **Contained, not replaced.** Nine-definer ownership/path inventory and exact client grant tests pass. Production portability/less-privileged replacement remains a release gate; see alternatives below. |
| F04 | A live Auth ban with an already issued JWT denies commands but existing RLS reads remain authorized by live app account/membership state. | **Limitation reproduced**, not silently changed. Disabling the private application gate immediately denies reads. No integrated Auth-ban/signout/account-deletion mechanism is implemented. |
| F05 | Twelve fresh issue operation IDs succeed in a burst, leaving twelve invite/receipt histories and only one pending invite. Idempotency and one-pending constraints are not abuse limits. | **Open production blocker.** Rate/quota/body-size controls are proposed, not installed. No external limiter or delivery is introduced. |
| F06 | CLI local Auth containers share a legacy HS256 signing secret, verified by in-memory comparison without printing it. Exact service-role token strings differ, so comparing token strings alone would miss shared signing authority. | **Local-only operational boundary.** API user-token verification accepts only this stack's public ES256 JWKS. That does not establish cryptographically independent privileged Auth credentials. Never reuse these local defaults as hosted secrets. Privileged cross-stack Auth HTTP access was not exercised/claimed. |
| F07 | No receipt pruning, HMAC rotation, durable audit telemetry, deployment rollback, backup restore or production gateway controls exist. | **Open, explicitly unimplemented.** Strategies and acceptance evidence are defined below. Retaining proof rows is not a product retention approval. |

The PostgreSQL reason for F01 is that per-schema privileges add to global defaults; they cannot subtract the default PUBLIC function grant. See [PostgreSQL 17 default privileges](https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html). The fix does not change defaults for Supabase-managed Auth roles or grant the application new Auth privileges.

## Elevated-function audit

All elevated functions use fixed empty search paths; sensitive application/Auth/extension references are schema-qualified, built-ins resolve through pg_catalog, and no function accepts dynamic SQL or a caller-chosen actor. PUBLIC execution is explicitly revoked at installation. Trigger helpers are invoker functions with no direct client EXECUTE. Ownership bypass inside reviewed definers is deliberate; table owners/operators are trusted, not constrained by the client RLS proof.

There are three definers in A, three in B.1 and nine in B.2 (with the same nine in the B.3 fork). B.3 catalog assertions verify eight application-owner definers plus exactly one Auth-owner bridge; no app Auth SELECT, no temporary Auth-owner schema CREATE left behind, no anonymous function execution, and exactly eight authenticated RPC/helper grants. Existing regression suites verify their corresponding actual restricted-role/HTTP boundaries. A/B.1/B.2 global future-function defaults remain a historical limitation until explicitly migrated; current installed function grants still pass their original tests.

### Can the Auth-owner helper be less privileged?

Potentially, but **no replacement is implemented or certified** here. Merely changing owner to the application role or granting a few SELECT columns does not bypass `auth.users` RLS safely. Do not solve that by granting BYPASSRLS or broad Auth-directory access.

| Candidate | Benefit | Additional risk/gate |
| --- | --- | --- |
| Dedicated nonlogin, non-BYPASS reader with minimal columns and narrowly scoped Auth RLS | Reduces owner authority; current-user lookup could remain transactional | Changes managed Auth permissions/policies; vendor support, upgrades, row-lock privileges and negative tests must be established |
| Synchronous minimal identity projection maintained within Auth changes | Command role reads only private application facts | Auth trigger/update failures can break signup; must atomically reflect confirmation/email/ban changes without stale granting state; introduces managed-schema coupling |
| Trusted server revalidation via Auth before command | Avoids direct Auth table reads from command role | Adds a service and privileged attestation protocol; TOCTOU between HTTP verification and SQL commit remains unless explicitly solved; client-supplied claims are insufficient |

Recommend a separately authorized local comparison before choosing. Keep this bridge prototype-only until current-email freshness, all Auth update lock orders, hosted ownership portability and least-privilege behavior are proven. The current actor Auth SHARE → account → space → invite order has tested confirmation races, but is not a proof of every GoTrue transaction. The architecture blueprint's sorted multi-user/scope locks also cover future sync/personal scopes absent here; this smaller actor-only protocol must not be copied into that larger graph without a new lock-order review. [Supabase Auth data guidance](https://supabase.com/docs/guides/auth/managing-user-data) warns that managed Auth details can change; the FK uses only its primary UUID.

## Invitation and transaction review

Verified in the inherited suite: 32 CSPRNG bytes; SHA-256 token storage; keyed recipient-email binding with no directory lookup; current confirmed mailbox rather than stale JWT email; 24-hour server expiry checked after locks; self/wrong-recipient/expired/revoked/consumed denial; one pending invite; exact-operation replay versus forbidden new-operation replay; actor/scope serialization and unique seat/active-account backstops. Nine two-request races observe **both** HTTP transactions at actual database lock waits before release. A post-mutation receipt-write fault proves full transaction rollback and safe retry. Sensitive errors are generic without SQL details/hints; no claim of timing indistinguishability is made.

The additional loss/replacement test discards the one-time response, replays the same operation to receive only the original metadata, then explicitly replaces it. All prior pending tokens fail and only the replacement accepts. Plaintext cannot be recovered from receipts. Provisional issue responses deliberately do not disclose registration/verification/couple status; a currently verified eligible recipient is required at acceptance. Local email delivery is not added. Privacy/production UX approval is not inferred from this experiment.

## Operational strategies — not implemented controls

| Rate limits and abuse | Bound authenticated issuer/account + source request bursts; durable transactional per-actor/scope quotas for new operations; stable retries do not consume new effects; generic errors, request-size ceilings and key-safe outcome categories. Avoid storing raw emails/tokens/IP indefinitely. | No new limiter exists. Twelve fresh operations actually succeed. Gateway/IP controls, distributed fairness, time windows, retry behavior and privacy-minimal counters need explicit limits and load/race tests. |
| HMAC key rotation | Separate current signing/binding key from retained verification versions. Issue under current version; accept under the invite's version. Revoke affected invites on key retirement/compromise. Preserve request-hash compatibility for existing receipt retries; rotation must not turn the same request into a different hash. | Single key/version only. Trusted secret custody, compromise procedure, backup/key access, staged rotation and retry/expiry tests unimplemented. Do not blindly rotate the current function's always-version-1 hash. |
| Idempotency expiration | Separate compact operation deduplication from result disclosure; choose a maximum retry horizon, retain a minimal spent marker/operation uniqueness long enough to prevent a deleted receipt becoming a fresh create/issue. ## Prototype-to-production gaps and unresolved policies

- A's passwordless synthetic session-user roles, B.1's fixed fixtures, all local trusted Docker/psql access and the custom disposable reset/ledger are test infrastructure only. No role mapping, generic A dispatcher or schema-reset routine should enter the application.
- B.3's snapshot still has six experimental tables, no production profile/content/sync/Storage/Realtime schema, no credential persistence and no Flutter provider integration. Closed spaces are unreadable by both former users as a conservative proof boundary, not a final survivor-archive policy. Unlink does not erase previously delivered bytes.
- Live reads use account/membership/space; Auth sessions and D08 native/web persistence are separate gates. Initial sensitive browser persistence remains prohibited by the endorsed direction; no client storage is added here.
- Current strict draft/paired counts and 24-hour invitation mechanics are within this authorized experiment, not blanket formal approval of every D06/D09 implementation detail. [DECISION_SPECIFICATION.md](architecture/DECISION_SPECIFICATION.md) remains authoritative: D01/D02 approved; D03 revision retained; P03/P04/P09 unresolved; technical endorsements remain pending their stated approval gates.
- No shared-data archive retention, account deletion/recovery, financial audit expiration, text recovery, exports, product feature, hosted Auth/OAuth, deployment or privacy policy is implemented. No legal retention duration is invented.
- Other unverified boundaries: TLS and reverse proxy hardening, managed Auth vendor upgrades, full lock graph/deadlock/load behavior, wrong-issuer/audience/algorithm matrix, independent credential rotation, multi-region operations and all crash schedules.

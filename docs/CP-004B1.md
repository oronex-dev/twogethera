## Actual authentication flow

- A/B are partners in one synthetic space; C/D are an unrelated synthetic couple. Local Auth Admin creates these test users with randomly generated passwords and verified email status. This fixture privilege is clearly separated from client assertions.
- All four obtain genuine signed ES256 user access tokens by calling the local Auth password-grant endpoint. The harness does not hand-sign JWTs, set SQL claims, impersonate database users or use an admin JWT on client requests.
- Additional unrelated/unpaired E is created through real signup. Sign-in before confirmation is rejected with `email_not_confirmed`. The harness reads E's verification link from local captured email, verifies it against the local Auth endpoint without following external redirects, then performs genuine password sign-in.
- Each real token is sent in the HTTP Bearer header alongside the local public API key. Five distinct users resolve to their own `auth.uid()` while using the same actual `authenticated` database role. Decoding token metadata is an assertion aid; signature acceptance is demonstrated by PostgREST HTTP, not by decoding alone.
- A naturally expiring Auth-issued token is retained unchanged until the verifier returns 401. A fresh genuine sign-in then restores identity access. The short 60-second access-token lifetime is an isolated-test setting, not a production policy approval.

No external email account, OAuth/SMTP provider, real personal information, hosted project or production secret is used. Synthetic users and captured messages remain only in this disposable project's local volumes. Repeated runs create fresh synthetic accounts; no account-deletion product flow or automatic deletion of Auth users exists.

## Minimal schema and authorization architecture

The prototype migration is [20261029000100_http_probe.sql](../proofs/cp004b1-http/supabase/migrations/20261029000100_http_probe.sql). It is not copied into root/application migrations. Automatic CLI migration application is disabled; only the sentinel-checked runner installs it after verifying the dedicated local project/database marker. Existing proof schemas are reset only under `twogethera:cp004b1:disposable:v1`; a normal default DB comment can be replaced on first bootstrap only after the project label/ports and absence of colliding probe schemas are checked.

Only three application tables exist in the prototype:

| Table | Purpose |
| --- | --- |
| `cp004b1.spaces` | UUID, draft/paired/closed state and irreversible closure timestamp |
| `cp004b1.memberships` | UUID, real Auth-user FK, same-space seat 1/2, active flag, unique historical seat/user and partial unique active-user index |
| `cp004b1.records` | UUID, space FK and synthetic text marker only |

No profile mirror, invitations, receipt stream, production module, deletion/retention, Storage or Realtime object is introduced. Auth and table fixtures are privileged setup, not client authorization evidence.

All three tables enable RLS. `authenticated` has explicit SELECT only; direct writes and anonymous table/function access are denied. Membership predicates derive the current principal from `auth.uid()` and check current active membership plus space state on each statement. An unpaired verified user or unrelated couple receives no foreign rows.

The exposed `whoami()` function is SECURITY INVOKER, returning only the caller's UUID and database role. A narrow owner-definer `can_read(uuid)` helper returns a boolean for the **current** caller, never another person's principal or rows. `leave_space(uuid)` checks the current authenticated principal/membership after locking the space, revokes memberships and closes it atomically, without deleting data or granting archives. A foreign caller receives a generic denied response with no data effects. Every function has fixed empty search_path/qualified application objects; PUBLIC EXECUTE is revoked, private helper schema is not API-exposed and the owner role is NOLOGIN/NOBYPASSRLS and not assumable by clients. Its intentional table-owner bypass applies only inside the reviewed three-table helpers.

Auth's `auth.users` table has independent RLS. We did **not** grant an application helper BYPASSRLS or broad Auth reads to work around it. The owner has only required Auth schema usage/primary-key REFERENCES for the membership FK, with no SELECT of private Auth rows. This B.1 proof relies on real confirmation enforced by Auth at sign-in plus live application membership. It does not implement fresh account-ban/email-verification rechecks after token issuance; those require a reviewed later account/identity contract.

PostgREST boots on the existing empty public namespace, then the guarded installer narrows runtime `pgrst.db_schemas` to `cp004b1` and reloads schema/config. The private helper/Auth schemas stay unexposed. No verification setting is disabled to obtain successful responses.

## Membership and revocation backstops

Database constraints cap seats at two and enforce one active space/account. Deferred triggers enforce draft=one, paired=two and closed=zero active members at commit. Membership UUID/scope/user/seat cannot be reassigned, revoked seats cannot reactivate and a closed space cannot reopen or accept a replacement partner. These are prototype mechanisms under the current mission, not formal approval of every D09 implementation detail.

The two couples are seeded transactionally using actual Auth UUIDs. Client HTTP cannot create or modify membership directly. Additional **privileged constraint probes**, explicitly distinct from RLS tests, attempt third seats, duplicate seats, an already-active user in another space, invalid committed counts, reopening/resurrection and replacement. Failures must leave persisted counts unchanged.

The noncreator B executes `leave_space` using the real user JWT. The **same still-valid A/B tokens** subsequently receive empty shared-record results and 403 on further former-space leave attempts, while `whoami()` still confirms their identity. This proves current authorization loss rather than treating token expiry as revocation. Records remain physically present. No archive rights, retention period or remote-erasure claim is selected.

Error-response checks reject synthetic private markers, passwords and privileged key material. Standard structural errors can name an exposed table; no claim of hiding all schema names is made.

The harness only uses the service-role local credential in a separate Auth fixture method restricted to `/admin/users`. No service-role Authorization header is used on the client PostgREST path. Superuser SQL is confined to probe installation, fixture/catalog inspection and direct constraint probes. Genuine token acceptance, user isolation, negative requests and leave/revocation are HTTP tests under actual client contexts.

## Known limitations and production risks

- This is not production Auth, a Flutter SDK integration, a hardened hosted deployment or a product-policy approval. Local HTTP does not establish TLS/session/device-security properties.
- A/B/C/D are admin-confirmed synthetic fixtures; only E exercises actual local confirmation delivery. External email, OAuth, password recovery, MFA, refresh/session invalidation, user enumeration and abuse/rate behavior are not validated.
- Membership creation/linking/invitation operations, general command idempotency and HTTP transaction races remain for CP-004B.2/later. This proof does not replace CP-004A's separate controlled-concurrency evidence.
- Fresh account-disable/ban/email-change checks, account registry/bootstrapping and token/session-to-account revocation need a dedicated design. An already issued JWT is not automatically invalidated by every Auth change. B.1 demonstrates membership revocation specifically.
- The verifier is intentionally limited to the proof's public ES256 key set; malformed/corrupt/expired-token checks do not establish every issuer/audience/algorithm/key-rotation edge case. No forged valid JWT test fixture is introduced.
- Default local CLI API/admin credentials are development-only and may be shared across projects. Loopback/project/volume guards and the separate ES256 user verifier are tested; possession of local Docker/admin access remains trusted. Never use this scaffold/default credential model in production.
- Only three-table helper safety is examined. No production Storage, Realtime, views, backups, recovery, financial records, retention or browser/native persistence security is proven.
- Repeated tests reset only their own schemas, leaving synthetic Auth accounts/mail and local containers/volumes for inspection. Do not run parallel copies or store real data. Missing tooling, rate limits and timeouts fail the suite; they do not become skips.
- Closed records remain inaccessible to both former members without deletion; this is a limited fail-closed experiment, not an approved archive audience/ownership policy or permission for indefinite retention. D03/P03/P04/P09 and other formal approval gates are unchanged.

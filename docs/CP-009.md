# CP-009 — Production Launch Preparation

## Prepared configuration

- Flutter release configuration reads `APP_ENV`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` (or legacy `SUPABASE_ANON_KEY`), and `APP_WEB_URL` at build time. Values are not stored in source. Only HTTPS hosted origins and client publishable/anon keys are accepted in staging and production.
- `tool/vercel_build.sh` pins Flutter 3.47.7, verifies the official Linux archive SHA-256 before extraction, validates these client build values, and produces `build/web` for Vercel. The Supabase key compiled into a Flutter client must be a publishable/anon key; it is public client configuration, never a service-role or secret key.
- `tool/build_web_release.sh` validates required values and builds the PWA for root-domain hosting. The Supabase client key is public client configuration; never supply a secret or service-role key.
- Supabase Auth email and recovery links return to `APP_WEB_URL/#/auth/callback`, matching Flutter's existing hash URL strategy. Add that exact URL to the project's allowed redirect URLs and set the hosted site URL to the web origin. Do not use broad production redirect wildcards.
- Local development keeps `LOCAL_AUTH_ENABLED`, loopback Supabase endpoints, synthetic `@example.invalid` identities, and the current in-memory session behavior.
- Dashboard preferences remain server-backed. Planner data is not placed in browser storage or a custom offline queue. Flutter's generated static asset cache is separate from authenticated data.
- `supabase/config.toml` remains a local-development configuration. Set production Site URL, allowed redirects, email sender/SMTP and Auth limits in the hosted project's settings after the actual domain and mail provider are selected.

## Hosted setup sequence

1. **Superseded for Private Beta V1:** the earlier broader-launch proposal was to create separate staging and production projects. The approved private-beta scope uses the existing `twogethera-beta` project only; do not create another Supabase project for this release. Keep project-owner access restricted, and never place project secrets in Git or Flutter build variables.
2. Configure the production site URL and allow only `https://<beta-domain>/#/auth/callback`. Configure a verified sender domain and production SMTP before testing email confirmation and recovery links.
   Configure the confirmation and recovery email templates to link directly to `{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=signup` and `{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=recovery` respectively. The app scrubs these one-time values from browser history before exchanging them. Keep the exact callback URL on the Auth allow-list.
3. Set the build environment variables in the selected CI/hosting provider's secret or environment settings. `SUPABASE_PUBLISHABLE_KEY` is intentionally public; no server-side secret is required by the Flutter app.
4. For the existing beta project, verify its identity in a trusted operator environment, inspect `supabase db push --dry-run`, and review all pending migrations before any separately authorized application. Do not target another project. Run authenticated RLS and invitation proofs against the beta only after migration and deployment authorization.
5. Configure the static host to serve Flutter files over HTTPS. The callback is in Flutter's URL fragment, so it does not require a server-side `/auth/callback` rewrite. Keep response headers/CSP compatible with Flutter's generated scripts and the Supabase API; do not cache authenticated API responses.
6. Build with `tool/build_web_release.sh`, install the PWA from the HTTPS origin, and validate sign-up, verification, sign-in, partner acceptance, planner isolation, preferences, sign-out, and re-entry after a browser restart.

### Managed-role compatibility review (2026-11-02)

- The five migrations use a narrow postgres-owned Auth identity/email bridge. They do not grant the app-private owner role access to Auth-managed rows or transfer functions to reserved `supabase_auth_admin`.
- Owner-owned membership and invitation tables store Auth UUIDs without cross-schema `auth.users` foreign keys. Server commands revalidate the current identity. Account deletion remains outside this milestone and still needs its approved lifecycle policy.
- Only the migration principal `postgres` is granted membership in `twogethera_membership_owner` so it can assume that NOLOGIN, non-BYPASSRLS role for DDL. No API role is a member.
- Migration 002 declares the `pgcrypto` dependency and schema-qualifies extension calls. Keep `app_private` out of the hosted Data API exposed-schema list; the local config exposes only `public` and `graphql_public`.
- A clean local database reset applied the first five migrations in order at that time. This confirms behavior on the local Supabase stack, not hosted database role constraints. A managed hosted migration review remains necessary before release.
- These migration-file corrections assume a fresh hosted project before its first migration push. If a target has already recorded any of versions 001–005, keep that history immutable and prepare a new forward correction migration instead.
- After the compatibility changes, CP-006A passed 21 scenario groups/182 assertions, CP-006B passed 11/229, CP-007 passed 198 checks, CP-008 passed 18 checks, and local database lint reported no schema errors.

### Private Beta V1 release gate (2026-11-08)

- **Current approved scope:** exactly the two existing partner identities. Disable public signup and invitations in managed Auth/provider configuration and retain the database allowlist. Do not onboard more accounts or couples.
- **Local implementation:** migration 028 contains the lifecycle, privacy-block, retention-job and minimized financial-audit schema/operations; migration 029 adds service-only queue claiming; migration 030 adds recovery metadata and audit guards; migration 031 fixes closure-receipt replay results; migration 032 no longer grants Auth-schema access to the restricted owner; and migration 033 checks recent password authentication using the signed Supabase `amr` claim. Do not change migration history already applied in a target. On any nonempty target, use forward-only migrations and review a dry run.
- **Historical local blocker, resolved:** during the earlier investigation, the local DB was responsive through migration 030/lint and later timed out, leaving migration 031 and CP-013 unverified at that time. After safe recovery, migration 031, migration 032, and the CP-013 rollback-only proof all completed locally; CP-014 also passed with real signed JWTs through PostgREST. Do not reset the project to recover it. None of these local results proves hosted migration compatibility or hosted authorization behavior.
- **Maintenance:** deploy the reviewed `private-beta-maintenance` Edge Function only after configuring its server-side environment (`APP_ENV`, `TWOTHERGA_EXPECTED_PROJECT_REF`) and a random `PRIVATE_BETA_JOB_TOKEN`. Supabase injects `SUPABASE_URL` and the legacy `SUPABASE_SERVICE_ROLE_KEY` into Edge Functions; do not attempt to upload those platform-provided values as custom secrets. Store the job token in Supabase function secrets and, if using Supabase Cron, in Vault for the scheduled request. Schedule authenticated POST calls, monitor nonzero failure counts and missed deadlines, and test retry behavior. `delete-account` also needs the expected project reference and a narrowly configured `PRIVATE_BETA_ALLOWED_ORIGINS` value. Neither function nor a scheduler is deployed/configured by this repository change.
- **Auth and identities:** in hosted Supabase, disable signup and invitation flows, configure callback Site URL/allowlist and verified SMTP, and verify only the two approved accounts. Never expose service-role material in Flutter or Dart compile-time defines.
- **Storage/privacy:** keep profile photos disabled. Verify private bucket policies, pointer revocation, object/derivative cleanup and failure retry in managed staging before enabling media. Confirm all query/search/RPC routes respect privacy blocks.
- **Backup/restore:** verify provider backup age meets the conditional 30-day maximum, then run a quarantined restore and prove deletion/revocation replay occurs before API access. This repository has no independent provider-surviving revocation ledger or configured restore gate; until proven, the approved backup target is a hard personal-data release blocker.
- **Web/Vercel:** deploy only after an approved build using `APP_ENV=production`, hosted `SUPABASE_URL`, public `SUPABASE_PUBLISHABLE_KEY`, and exact HTTPS `APP_WEB_URL`. Verify hash callback redirect allowlist, TLS, CSP report-only, HSTS/referrer/permissions headers and no-store behavior for sensitive responses. The owner reports that the beta is deployed on Vercel; this repository review did not change Vercel settings or deploy.
- **Operational/legal:** support-assisted export remains unavailable until a real contact, named operators, identity verification and encrypted delivery/deletion workflow are supplied and tested. Privacy Policy and Terms remain drafts pending qualified legal and product review. No legal compliance claim is made.

Private Beta V1 is **not release-ready** until hosted migrations 006–033 are reviewed and applied through the verified migration executor; the restricted owner does not require Auth-schema `USAGE` in the revised migration 032.

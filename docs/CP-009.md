# CP-009 — Production Launch Preparation

## Prepared configuration

- Flutter release configuration reads `APP_ENV`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` (or legacy `SUPABASE_ANON_KEY`), and `APP_WEB_URL` at build time. Values are not stored in source. Only HTTPS hosted origins and client publishable/anon keys are accepted in staging and production.
- `tool/build_web_release.sh` validates required values and builds the PWA for root-domain hosting. The Supabase client key is public client configuration; never supply a secret or service-role key.
- Supabase Auth email and recovery links return to the exact `APP_WEB_URL/auth/callback` route. Add that exact callback URL to the project's allowed redirect URLs and set the hosted site URL to the web origin. Do not use broad production redirect wildcards.
- Local development keeps `LOCAL_AUTH_ENABLED`, loopback Supabase endpoints, synthetic `@example.invalid` identities, and the current in-memory session behavior.
- Dashboard preferences remain server-backed. Planner data is not placed in browser storage or a custom offline queue. Flutter's generated static asset cache is separate from authenticated data.
- `supabase/config.toml` remains a local-development configuration. Set production Site URL, allowed redirects, email sender/SMTP and Auth limits in the hosted project's settings after the actual domain and mail provider are selected.

## Hosted setup sequence

1. Create separate staging and production Supabase projects in the approved account and region. Enable project MFA and restrict database-owner access. Do not place project secrets in Git or Flutter build variables.
2. Configure the production site URL and allow only `https://<beta-domain>/auth/callback`. Configure a verified sender domain and production SMTP before testing email confirmation and recovery links.
   Configure the confirmation and recovery email templates to link directly to `{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=signup` and `{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=recovery` respectively. The app scrubs these one-time values from browser history before exchanging them. Keep the exact callback URL on the Auth allow-list.
3. Set the build environment variables in the selected CI/hosting provider's secret or environment settings. `SUPABASE_PUBLISHABLE_KEY` is intentionally public; no server-side secret is required by the Flutter app.
4. Link only the staging project from a trusted operator environment, inspect `supabase db push --dry-run`, then apply reviewed migrations to staging. Run the authenticated RLS and invitation proofs against staging before considering production.
5. Configure the static host to serve Flutter files over HTTPS and rewrite unknown paths, including `/auth/callback`, to `/index.html`. Keep response headers/CSP compatible with Flutter's generated scripts and the Supabase API; do not cache authenticated API responses.
6. Build with `tool/build_web_release.sh`, install the PWA from the HTTPS origin, and validate sign-up, verification, sign-in, partner acceptance, planner isolation, preferences, sign-out, and re-entry after a browser restart.

## Verification boundaries

Local migrations have been applied through CP-008 in the local Supabase project. Local PostgreSQL tests exercise real Auth JWTs and restricted PostgREST roles. This does not prove managed-hosted role privileges, production SMTP delivery, browser-host configuration, or live redirect behavior. Do not run `supabase link`, `supabase db push`, or deploy until a real project is supplied and the dry run is reviewed.

### Managed-role compatibility review (2026-11-02)

- The five migrations use a narrow postgres-owned Auth identity/email bridge. They do not grant the app-private owner role access to Auth-managed rows or transfer functions to reserved `supabase_auth_admin`.
- Owner-owned membership and invitation tables store Auth UUIDs without cross-schema `auth.users` foreign keys. Server commands revalidate the current identity. Account deletion remains outside this milestone and still needs its approved lifecycle policy.
- Only the migration principal `postgres` is granted membership in `twogethera_membership_owner` so it can assume that NOLOGIN, non-BYPASSRLS role for DDL. No API role is a member.
- Migration 002 declares the `pgcrypto` dependency and schema-qualifies extension calls. Keep `app_private` out of the hosted Data API exposed-schema list; the local config exposes only `public` and `graphql_public`.
- A clean local database reset applied all five migrations in order. This confirms behavior on the local Supabase stack, not hosted database role constraints. A managed staging dry run remains necessary before production.
- These migration-file corrections assume a fresh hosted project before its first migration push. If a target has already recorded any of versions 001–005, keep that history immutable and prepare a new forward correction migration instead.
- After the compatibility changes, CP-006A passed 21 scenario groups/182 assertions, CP-006B passed 11/229, CP-007 passed 198 checks, CP-008 passed 18 checks, and local database lint reported no schema errors.

## Beta blockers and known limits

- No hosted deployment settings were provided for this review. Although local CLI link metadata may exist, no hosted database commands or connections were made. Beta domain, hosting provider, and SMTP sender are still unconfigured here.
- Managed staging has not confirmed migration runner membership, ownership transitions, Auth row-lock behavior, and API schema exposure. Verify these before production and preserve the current owner-role boundary.
- Web sessions are memory-only. Reloading/closing the browser signs the user out; persistent browser credentials are intentionally not enabled.
- Shared-data privacy removal, archive/recovery, and account-deletion handling still depend on unresolved privacy decisions. Resolve and disclose these policies before onboarding real couples with sensitive shared content.
- Production rollout, monitoring/alerting, backups/PITR configuration, incident response and rollback have not been configured or tested.

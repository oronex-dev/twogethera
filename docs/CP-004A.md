## Authorization and identity boundary

Tests use **genuine separate connections as restricted PostgreSQL roles**: `cp004a_test_a` through `cp004a_test_l`, and `cp004a_anon`. These roles have no superuser, BYPASSRLS, database/role-creation or replication privileges, and no membership in the owner role. Synthetic identity comes from `session_user`, not writable JWT settings or a caller-supplied actor. Attempted role/session-identity escalation and a spoofed JWT-claim setting are tested.

The synthetic clients are passwordless LOGIN roles using the existing trusted container-loopback rule; no password-based host identity flow or production account is created. Local Docker access is trusted. The application never receives these roles or connects to this database. This is a simulated authentication boundary, not Supabase Auth/JWT validation.

All six tables enable RLS. Ordinary client SELECT policies filter spaces, memberships and records by current membership and open space. Private identities/invites/receipts have no client access. Anonymous has schema usage only, with neither data nor function permissions. Client DML grants and DML policies are absent. Tests also temporarily grant DML on a populated test-record table, prove RLS independently rejects inserts and affects zero rows on UPDATE/DELETE, verify the existing row is unchanged, then revoke those grants.

A dedicated NOLOGIN/NOBYPASSRLS table-owner role owns the two schemas/functions. Its narrowly exposed SECURITY DEFINER command and read helper use empty fixed search_path and fully qualified objects. Table-owner bypass is intentional inside those functions; FORCE RLS is not used to create recursive membership checks. Ordinary clients cannot become this role. Public function EXECUTE is revoked; only the named command and scope-read helper are granted. No general SQL/table/actor mutation API exists.

Privileged `supabase_admin` is used for disposable setup, fixture manipulation, lock observation and direct constraint checks only. Member/anonymous authorization, command and replay assertions connect as the actual restricted roles; they do not rely on service-role behavior or a superuser session's temporary role switch.

## Membership and transaction invariants

- Seat CHECK 1/2 plus unique `(couple_id,seat)` caps historical capacity; no new/replacement seat after closure.
- Partial unique active `user_id` enforces one active space/account, including a draft.
- Deferred commit-time count triggers require draft=one active, paired=two, closed=zero. An invalid paired-space insert fails at commit.
- Membership user/scope/seat and revoked status cannot be rewritten/resurrected. Closed spaces cannot transition back or be reused.
- Guarded commands lock the acting identity first, then the scope, then relevant invite/record. Actor serialization protects two-space acceptance and operation-key races; scope serialization coordinates linking, record changes and unilateral unlink. No global application-wide lock.
- Every command rechecks live state after locking. Stale epoch/revision rejects without effects.
- Unlink is available to either partner, including the noncreator. It closes the scope/revokes active membership and blocks subsequent record/command/receipt access. This proof deliberately grants **no survivor archive access to either former member**; it does not choose production archive content or retention, purge shared history or claim remote erasure.

Data already returned by an in-flight request cannot be recalled. The tested revocation boundary concerns new statements after committed revocation and writes serialized after closure, not malicious clients' saved copies or every possible long-running isolation-level scenario.

## Invitations and idempotency

Synthetic recipient identities are privately bound to invitations and verified at acceptance; clients cannot edit verified flags. Token material is 256 bits: SHA-256 over three independent CSPRNG UUIDv4 values, returned once, with only a 32-byte digest stored. A 24-hour server deadline is rechecked using `clock_timestamp()` after locks. One pending invite is allowed; replacement revokes the earlier token. Unknown/wrong/expired/revoked/consumed tokens fail generically.

Acceptance inserts the second seat, changes paired state/epoch, marks the invitation accepted and writes its receipt in one transaction. A forced later error rolls all of them back. A new operation cannot reuse a consumed token; the exact previously committed actor/operation/payload can retrieve a sanitized current-authorized receipt once. No membership or mutation duplicates on retry. Changed payload under an existing operation ID is rejected.

Create/accept/record insert/edit/remove use actor-scoped operation UUIDs and canonical PostgreSQL JSONB request hashing. Receipts and effects commit together. Epoch/revision checks apply to new operations; a successful unchanged retry returns the existing result while current access still permits it. After unlink, old receipts cannot disclose former-scope results. Invite-issuance retries deliberately cannot recover the raw token; an explicit replacement is needed if the one-time token response is lost. Unlink retry cannot use an old receipt to regain former-scope access.

Tokens/credentials are never command-line arguments, checked-in fixtures, test output or receipt bodies. SQL is delivered over stdin. Test-session statement/error logging is disabled before sending potentially sensitive SQL; role-specific settings apply only in this disposable database. That is a local test safeguard, not a reviewed production logging/observability system.

## Security limitations and pending production decisions

This proves the scoped PostgreSQL behavior, not production safety. The following remain outside CP-004A:

- Real Supabase Auth/JWT, PostgREST/API views/RPC exposure, Storage/Realtime, device/session revocation, network/TLS and HTTP cache behavior. Separate DB proof is not an end-to-end hosted Supabase test.
- Production verified-email normalization/change, HMAC binding/key rotation, delivery and abuse/rate limits. Synthetic immutable UUID identities are used instead of assuming email text proves ownership.
- Full deadlock/load/availability coverage, every possible interleaving, long-lived repeatable-read snapshots, migrations/upgrades and production grants. Three controlled rounds per race are evidence for the tested schedule, not formal proof of all schedules.
- Archive eligibility/classification/expiry, ordinary recovery and financial audit horizon. D03 and P03/P04/P09 remain unresolved as recorded in [DECISION_SPECIFICATION.md](architecture/DECISION_SPECIFICATION.md); technically endorsed directions remain pending formal approval. Passing tests does not approve them.
- Privacy erasure, retention, backups, encryption/browser storage, real data outbox or cloud sync. No account deletion or data-lifecycle promise is implemented.

The proof database and uniquely prefixed roles remain for inspection and repeatable tests. They have no production purpose and must never receive real personal information. NULL-password client roles are not a host authentication design. The runner does not edit existing `pg_hba.conf`, Supabase configuration, standard Auth roles or the application schemas. Remove proof resources only through a separately reviewed, sentinel-checked cleanup; no automatic broad reset/drop is provided.

## Technical reference boundaries

The proof follows PostgreSQL 17 [row-security semantics](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html) and [function security/search_path guidance](https://www.postgresql.org/docs/17/sql-createfunction.html). These support the database mechanics, not production privacy approval or a claim that every race schedule has been verified.

## Invitation quota semantics

**Proof-only values:** five fresh successful issue/replacement operations per actor per fixed **server-UTC hour bucket**. It is not a rolling hour: up to ten may fit around adjacent bucket boundaries. The actor budget survives closing a draft and creating a different scope. It is independent of recipient registration/email, and does not reveal recipient identity state.

The wrapper first takes the existing actor lock and calls the private checked issue core. Exact committed retries return their prior metadata without charging again. A fresh success charges the durable budget in the same transaction; when exhausted, generic `PT429`/HTTP 429 rolls **all** replacement/receipt effects back, preserving the previous usable pending token. Invalid/self/stale/payload-conflicting commands do not become successful charges. Clients cannot choose the actor or server bucket. The existing unique pending-per-space index remains the pending capacity backstop; scope recreation cannot reset an actor's quota.

Real HTTP concurrency proves same-ID requests charge once (one raw-token response), and two new operations at the final available slot produce one 200/one 429 with five charges and one pending invite. An unrelated issuer's budget remains independent. An older-bucket fixture tests current server-bucket accounting without waiting a real hour; the clock is not mocked and requests have no caller-time override.

Unimplemented ingress protections: source/IP/distributed fairness, account-farming resistance, request/body ceilings, signup/recovery abuse, backend rate-limited delivery, Retry-After/backoff and external gateway enforcement. A database quota does not protect JSON parsing/signature verification from floods. Budget history cleanup is also unimplemented. No external limiter or mail delivery is configured.

## Receipt lifetime and cleanup

**Proof-only policy:** result availability expires after one server hour. Receipts have recorded/expiry timestamps and a retired marker. Replay checks expiry/retirement before returning a result, yielding HTTP 409 `operation_expired`; it never treats an expired ID as a new operation. Clients must reconcile current account/context and explicit intent, rather than automatically generate a new UUID and repeat a timed-out command.

The explicit maintainer compactor captures a server cutoff, locks candidate accounts in UUID order using `FOR UPDATE ... SKIP LOCKED`, then compacts expired receipts. This shares the command serialization point and skips actors held by an in-flight transaction. Fresh receipts are untouched. Compaction clears result JSON and request hash, retains the spent actor/operation key plus mandatory legacy scope/timestamp metadata, and is repeatable. Its limit bounds **actors**, not total rows for one actor; production batching must improve that bound.

Verified: fresh cleanup returns zero; actor-lock contention prevents compaction; after release expired rows compact once and a second run returns zero; expired create/issue IDs cannot recreate effects after closure; expired acceptance is denied before and after cleanup; two simultaneous retries after retirement both return 409 and membership remains two. Existing same-ID concurrent acceptance tests still pass before expiry.

Spent markers are intentionally **not deleted** during the proof's lifetime: deleting them would permit an old command to execute anew. This bounds result availability/compacted payload, not total marker count. The old FK-required scope metadata remains a production minimization/deletion-design gate. No scheduled cleanup worker exists: physical payload removal requires running maintenance; expiry denies delivery immediately, but does not automatically erase database bytes at one hour. Marker/budget quotas, scheduling, maximum replay horizon and eventual safe marker retirement remain production work. No shared-content, archive or financial audit retention policy is implemented or approved.

## Signing-key lifecycle evidence and limit

The passing suite uses the official CLI `gen signing-key --algorithm ES256`, captures private material in memory only, and supplies **only public JWK fields** to the actual PostgREST verifier. No token is hand-signed. Auth continues issuing tokens under its original key in this final suite.

1. Add the generated public key beside Auth's current JWKS: the original genuine JWT still succeeds.
2. Remove Auth's original public key from PostgREST trust: the **same unexpired token** returns HTTP 401. Its real `exp` is checked to distinguish loss of trust from expiry.
3. Restore original trust: that token succeeds again; disabling the application account still returns empty RLS reads, independently of valid key trust. Explicit account restoration restores permitted access.

This is a verified **verifier trust lifecycle**, not full Auth signer rotation. It does not prove new-signer adoption, Auth-managed overlap, refresh token behavior, automatic JWKS refresh, gateway/API-key rotation, multi-instance propagation or production caches. PostgREST here uses a manually refreshed public-JWKS snapshot in the guarded local database role. Removing a key from Auth configuration alone is not a tested immediate verifier-denial mechanism.

The earlier multi-key CLI append/restart exploration failed to complete reliably and was restored, as recorded above. No general claim is made that the CLI or managed product cannot rotate keys; only this environment's end-to-end procedure remains unverified. Supabase's [signing-key documentation](https://supabase.com/docs/guides/auth/signing-keys) distinguishes changing the signer from retiring verifier trust. A production rehearsal must prove the full supported process, overlapping/new tokens, retirement, refresh, cache reload and recovery before deployment.

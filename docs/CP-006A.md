# CP-006A — local membership and security foundation

**Status: CP-006A.1 HARDENING VERIFIED; READY FOR FINAL REVIEW.** This is an isolated local proof, not a production rollout. No remote push was created.

## Baseline and scope

Work began from a clean `main` at `501bbb67d148fb23757fe262f1106cd27b9ce854`. The approved Flutter foundation, CP-003A design, CP-004 proofs, CP-005 implementation, and architecture decision history were preserved. The root `supabase/config.toml` was inspected and left unchanged. Its Auth email confirmation setting is disabled for ordinary root-local development; CP-006A uses a separate local Supabase project with confirmation enabled and local Mailpit configured. The root local stack was not reset or migrated.

The single root migration, [`20261102000100_membership_foundation.sql`](../supabase/migrations/20261102000100_membership_foundation.sql), adds only:

- Couple-space states and immutable IDs, timestamps, row revisions, authorization/privacy epochs, and first-closure timestamp.
- Membership rows with fixed seats 1–2, Auth user foreign keys, unique couple/seat and couple/user constraints, and a partial unique index limiting each account to one active couple.
- Commit-time deferred cardinality checks: draft has one active member, paired has exactly two, and archived/purging has none.
- A non-login, non-superuser, non-BYPASSRLS owner for the membership tables and narrow security-definer helpers with fixed empty `search_path`.
- A current signed-principal Auth check that requires a confirmed email, non-anonymous/non-banned user, and an unexpired JWT.
- RLS-filtered scope/member reads, a shared-record eligibility predicate that requires paired state and exactly two active members, and an atomic idempotent `create_couple_space(operation_id)` command.

The only planner-shaped relation, `cp006a_test_shared_records`, is installed by the isolated test runner and is not in an application migration. It contains synthetic rows and tests D09: a draft/unpaired member must not read a shared planner record. Invitations, token generation/acceptance, unlink UI/API, product modules, archive retention, account deletion, Storage, Realtime, sync, and Flutter integration remain out of scope. D01, D02, D06, and D09 status is unchanged; no pending policy was approved.

## Local setup and test flow

The separate project uses loopback ports 59321–59324, project ID `twogethera-cp006a`, ES256 local Auth signing keys under an ignored `.local` directory, email confirmation enabled, and Mailpit. The helper refuses remote Docker overrides and verifies Docker project labels and loopback bindings. Startup output, Supabase status credentials, access tokens, and generated keys are captured or suppressed.

```sh
rtk proxy python3 -u proofs/cp006a-membership/start_local.py
rtk proxy python3 -u proofs/cp006a-membership/run_tests.py
```

The runner reads the canonical root migration and installs it only after checking the isolated database marker. It uses local Auth administration only for synthetic `example.invalid` test identities and setup. Auth verification state is checked from `auth.users`; the unverified test account cannot obtain a password-grant session. Client authorization uses genuine Auth-signed user JWTs through PostgREST with the local public API key and the actual `authenticated` database role. Service-role credentials are never used as client authorization evidence. Database operator SQL only installs the marked disposable fixture, performs isolated negative constraint probes, and inspects state/catalog outcomes.

The local CLI initially chose ports already occupied by CP-004B.3. Container/port inspection identified that conflict, so CP-006A moved to the unused 593xx range without stopping or changing the existing project. An initial test exposed PostgREST’s default local verifier behavior: a 60-second Auth JWT was rejected by Auth after expiry but a PostgREST request still carried an authenticated context. CP-006A now pins this isolated PostgREST verifier to the local Auth public ES256 JWKS and independently checks the signed JWT `exp` claim in the private database identity gate used by RLS and the create command. The check fails closed for missing/malformed/expired claims. The test distinguishes Auth rejection, a protected read filtered to HTTP 200 with `[]`, and an explicitly denied protected identity RPC. It does not claim that every PostgREST endpoint returns 401 for an expired token.

## Security boundaries and limitations

- The proof is local and synthetic. It does not establish hosted deployment behavior, production key custody, abuse/rate limits, email delivery, invitation acceptance, unlink implementation, archives, deletion, legal retention, or availability guarantees.
- The unverified identity is authoritatively represented in `auth.users` and cannot sign in. CP-006A does not exercise a full confirmation-email round trip; the separate CP-004B.1 proof does exercise signup, local captured confirmation email and subsequent real sign-in. Mailpit remains local only.
- PostgREST’s local verifier did not independently return an authorization error for every expired-token table request. The application DB gate checks signed `exp` and denies protected access; the test records the HTTP 200 empty RLS result and denied guarded RPC precisely. Before hosted production, verify the managed PostgREST/Auth verifier rejects expired JWTs end-to-end and retain the DB gate as defense in depth.
- `twogethera_membership_owner` is a NOLOGIN, non-superuser, non-BYPASSRLS role and owns the two RLS tables. PostgreSQL table owners bypass RLS unless `FORCE ROW LEVEL SECURITY` is enabled; the narrowly scoped helper needs to inspect the current membership rows without recursively re-entering the same membership policy. API roles receive no DML grants, cannot assume the owner role, and can call only the named create command. Review whether managed Supabase can support this exact owner/grant bridge before promoting the migration; do not add BYPASSRLS casually.
- The Auth-owned verification helper uses local Supabase Auth role ownership/column access. Rehearse this grant/owner transfer against the target managed Supabase role model before production migration. Do not assume local superuser behavior implies hosted portability.
- Deferred count triggers, unique indexes, command locking, and rollback were exercised on this local PostgreSQL 17 stack. This bounded suite is not exhaustive concurrency model checking.
- This is the first root application migration, validated on a clean isolated project. There is no earlier root migration to perform a populated N-1 upgrade against. Repeatable clean proof runs rebuild only CP-006A-marked objects in its dedicated disposable database; they do not reset the root database or CP-004 projects.
- A fresh `supabase status` command prints local demo credentials; the test harness captures JSON and never echoes credential fields. Do not paste raw status output into logs/reports.

## CP-006A.1 independent-audit remediation

The independent CP-006A audit's initial findings are retained as historical context: nullable role comparison, incomplete owner-role checks, inconsistent archived membership state, weak draft creator cardinality, unproven request overlap, incomplete rollback assertions, and a private-schema probe sent to the public profile.

| Finding | Remediation | Verification evidence |
| --- | --- | --- |
| Missing JWT `role` could pass SQL NULL logic | `current_identity_is_verified` now uses `auth.role() IS DISTINCT FROM 'authenticated'`. A signed ES256 token from the disposable local Auth key uses a real synthetic subject and valid expiry but omits `role`. | HTTP read/command denial plus direct database gate returning NULL. The test token is never printed. |
| Owner role guard omitted NOINHERIT and role memberships | Migration requires NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS, NOINHERIT, expected marker, and no incoming/outgoing role membership. | Negative guard tests verify both membership directions and INHERIT fail with SQLSTATE 42501, then restore the role. |
| Archived membership state contradicted timestamp transition | CP-006A membership states are only `active` and `revoked`; active-to-revoked sets `revoked_at` on the server. | Unsupported `archived` state rejected; actual revoke path checks non-null timestamp. |
| Draft could be completed by a replacement seat | Deferred invariant requires the one active draft member to occupy seat 1. Paired spaces require exactly two active members. | Replacement-seat transaction fails deferred check and leaves no draft row. No invitation or pairing operation is added. |
| Six requests did not prove overlapping database work | Six HTTP clients synchronize with a barrier. A temporary DB gate holds the first insert while peers queue on the actor advisory lock. | `pg_stat_activity` observed one `PgSleep` and five lock waits; exact one HTTP success/five HTTP conflicts; final state is one space, one active membership, one receipt. |
| Rollback test checked only active memberships | Injected receipt trigger raises fixed SQLSTATE `PT500` and message `cp006a_injected_receipt_failure`. | HTTP response code/message asserted exactly; all couple-space, membership, and receipt counts plus operation-specific receipt count are equal before/after. |
| Private helper probe used public profile | HTTP probe explicitly requests `app_private` in both profile headers. | Asserted HTTP 406 with PostgREST code `PGRST106`; config exposes only `public`. |

The CP-006A.1 run reports **21 scenario groups and 182 `require()` checks separately**. The above concurrency and JWT claims were verified against the isolated real local Auth, PostgREST, and PostgreSQL stack; clients used signed user tokens and not service-role authorization. Flutter analysis passed, all 88 unit/widget tests passed, Dart formatting found no changes in 38 files, and the final `git diff --check` passed. The CP-004B.1/B.2 suites were not rerun.

Membership lifecycle remains intentionally narrow: this migration does not implement unlinking, archived member entitlements, survivor archives, invitations, or replacement membership. D01/D02 and unresolved P03/P04/P09 remain as recorded; this proof does not approve them. The original creator is represented by immutable seat 1. Any future pairing command must be separately designed and tested to preserve this constraint.

CP-004B.1 and CP-004B.2 outcomes above are historical and were not rerun for CP-006A.1. The managed-Supabase role ownership/column bridge and expired-token behavior remain portability checks before hosted use.
